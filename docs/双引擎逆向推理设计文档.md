# 双引擎逆向推理框架 设计文档

**版本** v0.1 ｜ **状态** 待评审 ｜ **日期** 2026-11-17

---

## 1. 目标与范围

### 1.1 要解决的问题

在给定算力预算下，把任务成功率做上去，同时让单位任务成本随时间单调下降。手段是：把可复用的判断从"每次调模型"变成"查规则"，把链路结构从"正向试错"变成"从目标反推"。

### 1.2 明确的非目标

**不追求全局最优。** 全局最优需要三个前提同时成立：完备的分解空间、精确的成本与成功率模型、可采纳的启发函数。三者在本场景下都不成立。本设计的目标是**预算约束下的近似最优**，度量口径为"同等成本下的成功率提升"与"同等成功率下的成本下降"。

### 1.3 适用域界定

| 适用 | 不适用 |
|---|---|
| 目标可判定、有客观验收标准 | 目标模糊、验收靠主观感受 |
| 存在可复用的判断模式（同类问题反复出现） | 每题都全新的长尾任务 |
| 领域知识可以形式化为条件-结论结构 | 领域知识主要是审美、风格、开放创作 |

界定这一条是本文档最重要的部分。框架在适用域内收益显著，越界使用会退化成"用规则硬套灵活性任务"，两头不讨好。

## 2. 设计原则

| 编号 | 原则 | 含义 | 违反后果 |
|---|---|---|---|
| P1 | 验收外置 | 任何"完成"判定由外部谓词给出，不接受模型自评 | 系统无法闭环，失败不可见 |
| P2 | 符号优先 | 能用规则判定的路径不调模型 | 成本失控，且不可解释 |
| P3 | 记录先行 | 结构化决策轨迹先于任何优化落地 | 无数据可挖，规则只能手写 |
| P4 | 单项可回滚 | 规则、路径、预算策略均可独立关闭 | 出问题时只能全量回退 |

P1 与 P3 是硬约束，不满足则整个框架不成立；P2 与 P4 是优化项，可以在 P0 阶段暂缺。

## 3. 总体架构

```
┌─────────────────────────────────────────────────────┐
│ L4 编排层  Orchestrator                              │
│    目标选择 · 预算分配 · 路径开关（符号/模型/双跑）    │
├─────────────────────────────────────────────────────┤
│ L3 推理层  BackwardEngine                            │
│    AND-OR 展开 · 回溯 · 剪枝 · 证明树构造             │
│    禁止：网络调用、模型调用、文件写入                  │
├─────────────────────────────────────────────────────┤
│ L2 规则层  RuleStore                                 │
│    事实库 · 规则库 · 候选池 · 验证器 · 优先级仲裁      │
├─────────────────────────────────────────────────────┤
│ L1 执行层  Executor                                  │
│    工具调用 · 模型调用 · 验收谓词求值                  │
├─────────────────────────────────────────────────────┤
│ L0 记录层  Recorder                                  │
│    结构化轨迹 · 事件溯源 · 回放 · 归因                │
└─────────────────────────────────────────────────────┘
```

### 3.1 逐层职责

**L0 记录层**：所有事实的唯一来源。不是日志模块，是数据底座。后续每一个优化都从这里取数。

**L1 执行层**：唯一允许产生副作用的地方。工具调用、模型调用、验收求值全部收口于此，便于统一限流、计费、超时。

**L2 规则层**：管理规则的全生命周期（候选/激活/退役），负责冲突仲裁。规则不是静态配置，是有状态的对象。

**L3 推理层**：纯函数。同样输入必然同样输出，可完整重放。**禁止任何外部调用**——这条约束保证逆向链的确定性和可测试性。

**L4 编排层**：决定做什么、给多少预算、走哪条路径。是唯一知道全局状态的一层。

### 3.2 为什么这样分层

分层的目的不是"看起来有结构"，而是把决策频率不同的东西分开：

| 层 | 决策内容 | 触发频率 | 状态保持 |
|---|---|---|---|
| L4 | 选目标、分预算、切路径 | 每任务 1 次 | 全局 |
| L3 | 展开多深、走哪条 OR 分支 | 每失败点 1 次 | 单次调用内 |
| L2 | 规则是否命中、冲突如何仲裁 | 每次匹配 | 持久 |
| L1 | 用什么工具、什么模型 | 每个叶子 1 次 | 无 |

频率差异决定了缓存与校准该放在哪一层：L4 值得积累跨任务先验，L3 适合做单次内的记忆化，L1 只做实时缓存。

## 4. 核心数据结构

### 4.1 Goal（目标节点）

```python
@dataclass
class Goal:
    id: str
    predicate: str            # 目标谓词，如 "可签约"
    args: tuple               # 参数，如 ("A公司",)
    parent: str | None        # 父节点，用于构造证明树
    depth: int                # 展开深度，用于限深
    verifier: Callable        # 验收谓词，返回 bool
    budget: int               # 分配到的预算
    status: str               # pending | running | ok | failed | pruned
```

**`verifier` 挂在节点上，不在流程里。** 这是 P1 的物理保证：想绕过验收就必须改数据结构，而不是改流程。同时它让"验收"成为节点的固有属性，可被静态检查——没有 verifier 的节点不允许被执行。

### 4.2 Rule（规则）

```python
@dataclass
class Rule:
    id: str
    head: str                 # 结论谓词
    body: list[str]           # 前提谓词列表，全为 AND
    status: str               # candidate | active | retired
    source: str               # "human" | "llm:<trace_id>"
    confidence: float         # 置信度，来自回放统计
    hit_count: int
    fail_count: int
    created_at: datetime
    last_hit_at: datetime
```

**`source` 字段必须记录。** 它支撑三件事：来源归因（出问题时知道是谁引入的）、批量回滚（可按来源一次性下线）、质量分层（人工规则与模型规则用不同的验证阈值）。

**`body` 只支持 AND，不支持 OR。** OR 由 L3 在展开时通过多条同 head 规则表达。这个限制是刻意的：规则内部的 OR 会让冲突仲裁复杂度指数上升。

### 4.3 Trace（执行轨迹）

```python
@dataclass
class Step:
    node_id: str
    input_hash: str           # 输入指纹，用于回放匹配
    action: str               # 实际执行的动作
    output: Any
    judgment: str             # 离散判断结果，枚举值，非自然语言
    cost: int                 # token 数或调用次数
    latency_ms: int
    ts: datetime

@dataclass
class Trace:
    task_id: str
    goal_id: str
    steps: list[Step]
    outcome: str              # success | failure | abandoned
    total_cost: int
```

**`judgment` 必须是枚举值。** 这是整个框架的枢纽字段：它是将来规则的作用点、回放比对的基准、冲突检测的依据。存成自然语言就等于没存。

### 4.4 Candidate（候选规则）

```python
@dataclass
class Candidate:
    rule: Rule
    support: list[str]        # 支持该规则的 trace_id 列表
    counter: list[str]        # 反例 trace_id 列表
    evidence: str             # 挖掘时的归纳依据
    verdict: str              # pending | accepted | rejected
```

`support` 与 `counter` 是灰度对比的基础。只有 support 没有 counter 的候选不允许进入 active 态——这是防止过拟合的硬门。

## 5. 核心流程

### 5.1 求解循环

```python
def solve(goal: Goal, budget: int) -> Result:
    # 1. 正向短路：已有事实能否直接推出
    if closure_has(goal):
        return Result.ok(proof=[], cost=0)

    # 2. 预算可行性下界检查
    if budget < lower_bound(goal):
        return Result.fail("insufficient_budget")

    # 3. 逆向展开（纯符号，L3）
    branches = engine.expand(goal, width=W, max_depth=D)
    if not branches:
        return fallback_llm(goal, budget)      # 规则未覆盖

    # 4. 按 收益/成本 排序后逐一尝试
    for b in rank_by_gain_over_cost(branches):
        sub_budgets = allocator.split(b, budget)
        results = [solve(s, sub_budgets[i])
                   for i, s in enumerate(b.subgoals)]
        if all(r.ok for r in results):
            return Result.ok(proof=b, cost=sum(r.cost for r in results))

    # 5. 全部失败 → 模型兜底，同时产出候选规则
    return fallback_llm(goal, budget)
```

### 5.2 三个关键点

**正向短路在前。** 逆向展开代价虽然低，但也是一次完整搜索。先用闭包判一次，能命中的直接返回，实测这一条能砍掉相当比例的调用。

**`rank_by_gain_over_cost` 的排序函数**：

```
priority(n) = (1 - p(n)) × L(n) / cost(n)

p(n)    该节点当前的成功率估计
L(n)    该节点判断错误的损失（下游返工量）
cost(n) 该节点的预期开销
```

排序依据是"这里的判断有多不可靠 × 错了有多痛"，而非"这个任务有多难"。难但已经确定的节点优先级低，简单但一错到底的节点优先级高。

**`fallback_llm` 的返回契约。** 它必须同时返回两样东西：答案，以及一条候选规则。这条契约保证每次模型调用都在为规则库添砖，而不是纯消耗。返回结构：

```python
@dataclass
class FallbackResult:
    answer: Any
    ok: bool
    candidate_rule: Rule | None    # 本次判断可复用的模式
    trace_id: str                  # 关联轨迹，供后续挖掘
```

## 6. 模块清单

| 模块 | 职责 | 输入 | 输出 | 禁止 |
|---|---|---|---|---|
| Recorder | 记录结构化轨迹 | 每步执行结果 | Trace | 丢失 judgment |
| BackwardEngine | AND-OR 展开与回溯 | Goal, RuleStore | 分支列表 | 网络/模型调用 |
| BudgetAllocator | 预算切分 | 分支, 总预算 | 子预算数组 | 超发预算 |
| Executor | 叶子执行 | Action | Output + 验收结果 | 自评完成 |
| RuleMiner | 从 Trace 挖候选 | 轨迹批 | Candidate 列表 | 直接写 active |
| RuleValidator | 回放验证 | Candidate | verdict | 跳过 counter 检查 |
| RuleStore | 规则生命周期 | 各模块请求 | Rule 查询结果 | 无仲裁地返回冲突规则 |

## 7. 规则生命周期

```
   挖掘产出
      │
      ▼
  candidate ──回放通过───▶ active ──命中率衰减──▶ retired
      │                      │                      │
      └──验证失败──▶ 丢弃      └──上线后误判超标──► 回退 candidate
```

**状态迁移的硬条件：**

| 迁移 | 条件 |
|---|---|
| candidate → active | support ≥ 5，counter = 0，回放不误伤其他样本 |
| active → retired | 连续 30 天零命中，或命中失败率 > 20% |
| active → candidate | 灰度期间与模型结果不一致率 > 10% |

**retired 不是删除。** 保留记录但不再参与推理，这样规则库有历史可查，也支持"当时为什么下线"的追溯。

**规则库必须有容量上限。** 建议按域设定阈值（如单域 ≤ 300 条）。超过阈值时强制做一次退役评估。没有上限的规则库在 12-18 个月内必然腐化到不可维护。

## 8. 分阶段实施

| 阶段 | 模块 | 产出物 | 验收标准 | 预估 |
|---|---|---|---|---|
| P0 影子运行 | Recorder + Executor + 最小编排 | 结构化轨迹库 | 10 个真实任务，决策点记录率 100%，judgment 全部枚举化 | 2-3 周 |
| P1 挖掘 | + RuleMiner | 候选规则池 | ≥20 条候选，每条带 support 与 counter | 2-3 周 |
| P2 验证 | + RuleValidator | 激活规则集 | 回放通过率 > 80%，误伤率 < 5% | 2 周 |
| P3 逆向 | + BackwardEngine | 符号路径 | 符号路径可独立完成 ≥ 40% 高频任务 | 3-4 周 |
| P4 双跑 | + BudgetAllocator | 双跑对比报告 | 差异样本 100% 可解释 | 2 周 |
| P5 切换 | 全部 | 默认路径切换 | 成本降 > 30%，成功率不低于基线 | 2 周 |

### 8.1 实施顺序的理由

**P0 先做 Recorder，不做推理引擎。** 这是最容易走错的一步。推理引擎依赖规则库，规则库依赖数据，数据来自记录。先做引擎的结果是空转——没有规则可跑，只能手写几条玩具规则演示，演示完就搁置。

Recorder 单独就有价值：系统从黑箱变成可观测，出问题能定位到具体哪一步判断错了。这个价值在 P0 就能兑现，不需要等后续阶段。

**P3 排在第四位**，因为它是前置依赖最多的一环。

## 9. 风险登记

| 编号 | 风险 | 等级 | 缓解 |
|---|---|---|---|
| R1 | 适用域判断错误，把开放式任务硬套封闭域框架 | 高 | 立项前用 20 个真实任务做适用性预判 |
| R2 | 模型输出被当作真值，错误固化为规则 | 高 | 强制 counter 检查；保留人工复核抽样（≥5%） |
| R3 | 规则库超线性膨胀，维护成本吃掉收益 | 高 | 容量上限 + 强制退役评估 + 冲突检测 |
| R4 | 目标形式化失败，无法转成可判定命题 | 高 | 前置一道目标澄清环节，不可澄清的任务直接拒收 |
| R5 | 预算估计无数据支撑，冷启动期分配失真 | 中 | 冷启动期用固定档位，不做动态分配 |
| R6 | 长尾节点样本不足，p(n) 估计方差大 | 中 | 对样本量 < 20 的节点回退到域级先验 |

## 10. 开放问题

1. **目标形式化的自动方法**：如何把"把这个事办妥当"转成可判定命题？目前只能靠人工澄清，这是框架外的一环，但没有它整个链路起不来。
2. **跨域规则迁移**：A 域的规则能否复用到 B 域？如果能，规则库的边际成本会显著下降；如果不能，每个域都要重建一遍。
3. **真值来源**：除人工复核外，是否存在低成本的外部真值（下游系统反馈、用户行为、日志比对）？这一条决定 R2 能否真正缓解。
4. **模型升级时规则库怎么办**：底层模型换代后，用旧模型行为蒸馏出的规则可能整体失准，需要重新校准还是整体重建？

## 11. 术语

| 术语 | 含义 |
|---|---|
| 逆向链 | 从目标命题出发，匹配规则头，把规则体变为子目标，递归至事实或失败 |
| AND-OR 图 | 分解产生的搜索图，AND 节点需全部子目标成立，OR 节点任一成立即可 |
| 正向短路 | 展开前先用事实闭包判定，命中则跳过搜索 |
| 影子运行 | 不改变主路径，仅并行记录，用于积累数据 |
| 候选规则 | 从轨迹中挖掘出、尚未通过验证的规则 |
