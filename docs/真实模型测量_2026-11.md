# 真实模型小样本测量：N 份候选到底有没有用

**日期** 2026-11-18 ｜ **模型** DeepSeek（`deepseek-chat`） ｜ **样本** 8 个任务 × 3 份候选（含 3 个严格验收）
**复跑** `zsh -ic 'python3 tools/real_measure.py'`（key 在 `~/.zshrc`；读数写 `runs/measure/readings.jsonl`）

---

## 一句话结论

**在这 8 个可机检的任务上，候选选择没有带来可测的通过率收益**：single 与 best 都是 8/8，
单份失败 0、救回 0；评审分均值 +6.9，但全部来自 `intro` 一例（两份都过验收，属评审噪声）。
best-of-N 作为“失败保险”在本批样本里没被触发。

## 方法与判据

- 每个任务：DeepSeek 生成 3 份候选（temperature=0.9，「第 N 版」换措辞），逐份写目标文件 → 跑外部验收命令；
- 通过验收的候选交给 `judge-ds-v1` 按固定 rubric（准确/完整/可执行/无冗余，各 25 分）打分；
- `single` = 第 1 份候选，`best` = 通过者里评分最高的一份；两者用同一套验收与评审。

| 任务 | single | best | Δ分 | 选中 | wall |
|---|---|---|---|---|---|
| intro（两行介绍 nixiang） | pass | pass | +0 | 1 | 3902ms |
| points（三条要点，过程优先） | pass | pass | +4 | 2 | 3019ms |
| json（一行 JSON） | pass | pass | +0 | 1 | 3670ms |
| code（一行 Python 输出 7） | pass | pass | +0 | 1 | 3265ms |
| lines（五行双环说明） | pass | pass | +0 | 1 | 3274ms |
| **汇总** | **5/5** | **5/5** | **+0.8** | — | **3426ms** |

## 怎么读这个数

1. **简单可判定任务已经饱和**：验收命令只查关键词/行数/输出，模型第一份就过；选择器没有提升空间。
2. **评审分也几乎不动**：唯一 +4 的 `points` 是评审对结构更完整的一份多给了分，但两者都过验收。
3. **成本是实打实的**：3 倍候选 + 3 次评审，墙钟约 3.4 秒/任务；在简单任务上不划算。
4. **与之前 311 vs 223 的区别**：那是 `wc -m` 的长度分，长文本自然“赢”；这次用 rubric 评审，收益消失——
   说明**评分器的选择决定结论**，长度分不能当质量。

## 第二轮：加严格验收（2026-11-18，8 任务）

第一轮 5 个任务单份全过，无法区分“候选选择有没有用”。于是加 3 个严格验收任务
（三行 `- ` 列表、只含两个键的 JSON、恰好两行且每行 ≤15 汉字），再跑一遍：

| 任务 | single | best | Δ分 | 选中 | wall |
|---|---|---|---|---|---|
| intro | pass | pass | +55 | 3 | 3014ms |
| points | pass | pass | +0 | 1 | 3717ms |
| json | pass | pass | +0 | 1 | 3395ms |
| code | pass | pass | +0 | 1 | 2487ms |
| lines | pass | pass | +0 | 1 | 2797ms |
| strict-bullets | pass | pass | +0 | 1 | 2437ms |
| strict-json | pass | pass | +0 | 1 | 3542ms |
| strict-lines | pass | pass | +0 | 1 | 2956ms |
| **汇总** | **8/8** | **8/8** | **+6.9** | — | **3043ms** |

`single_fail=0 rescued=0 rescue_rate=0.00`。

读法：
- 严格验收也没让第一份失败——模型对这类格式要求一次就过；没有失败样本，“救回率”无从测。
- `intro` 的 +55 是评审对另一份的偏好，不是质量事实；两份都过验收，选择器只是在两个合格品里换了一个。
- 要真正测“保险价值”，需要更难的验收（多文件、跨步骤、隐含约束）或更弱的模型；这批样本做不到。

## 第三轮：难任务（2026-11-18，4 任务）

前两轮要么单份全过，要么没有失败样本。第三轮造 4 个更难的任务：shell 脚本
（条件复制）、Python 求和、严格 JSON 类型、恰好 20 个汉字。

| 任务 | single | best | Δ分 | 选中 | wall |
|---|---|---|---|---|---|
| hard-shell | pass | pass | +0 | 1 | 2868ms |
| hard-python | pass | pass | +4 | 3 | 3246ms |
| hard-json | pass | pass | +0 | 1 | 2418ms |
| hard-exact | **fail** | **fail** | +0 | 0 | 90ms |
| **汇总** | **3/4** | **3/4** | **+1.0** | — | **2156ms** |

`single_fail=1 rescued=0 rescue_rate=0.00`。

读法：
- `hard-exact` 三份候选全部没做到“恰好 20 个汉字”——这是**系统性失败**（能力边界），不是采样波动；
  多候选救不了它，换多少份都一样。
- 其余 3 个任务第一份就过，没有救回场景。
- 所以 best-of-N 的价值边界清楚了：**只对“偶发失败”有用，对“稳定做不到”无用**；
  系统性失败要靠改验收反馈/换方法/降级，不是加候选。

## 限制（别当业务结论）

- 5 个任务、单次运行、全部是短小的确定性写作任务，不是你的业务任务；
- `judge-ds-v1` 与人类一致性未校准（缺标注样本）；
- 没有测长任务/开放创作/研究型任务——那些才可能从多候选中受益；
- 未测失败重试、预算耗尽、多 Agent 并行下的评审成本。

## 落到设计上的判断

- 候选选择保留为**能力**（复杂任务/高预算时用），不作为默认路径；
- 默认路径仍是：能确定性执行就单份，验收不过再重试/多候选；
- 要证明候选选择在业务上有用，需要“开放任务 + 校准后的 rubric + 真实数据”，这三样当前都缺。
