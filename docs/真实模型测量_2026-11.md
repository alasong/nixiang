# 真实模型小样本测量：N 份候选到底有没有用

**日期** 2026-11-18 ｜ **模型** DeepSeek（`deepseek-chat`） ｜ **样本** 5 个任务 × 3 份候选
**复跑** `zsh -ic 'python3 tools/real_measure.py'`（key 在 `~/.zshrc`；读数写 `runs/measure/readings.jsonl`）

---

## 一句话结论

**在这 5 个可机检的小任务上，候选选择没有带来可测的质量收益**：single 与 best 都是 5/5 通过，
评审分平均只差 +0.8；代价是 3 倍调用与约 3.4 秒/任务。best-of-N 是保险，不是质量放大器。

## 方法与判据

- 每个任务：DeepSeek 生成 3 份候选（temperature=0.9，「第 N 版」换措辞），逐份写目标文件 → 跑外部验收命令；
- 通过验收的候选交给 `judge-ds-v1` 按固定 rubric（准确/完整/可执行/无冗余，各 25 分）打分；
- `single` = 第 1 份候选，`best` = 通过者里评分最高的一份；两者用同一套验收与评审。

## 怎么读这个数

1. **简单可判定任务已经饱和**：验收命令只查关键词/行数/输出，模型第一份就过；选择器没有提升空间。
2. **评审分也几乎不动**：唯一 +4 的 `points` 是评审对结构更完整的一份多给了分，但两者都过验收。
3. **成本是实打实的**：3 倍候选 + 3 次评审，墙钟约 3.4 秒/任务；在简单任务上不划算。
4. **与之前 311 vs 223 的区别**：那是 `wc -m` 的长度分，长文本自然“赢”；这次用 rubric 评审，收益消失——
   说明**评分器的选择决定结论**，长度分不能当质量。

## 限制（别当业务结论）

- 5 个任务、单次运行、全部是短小的确定性写作任务，不是你的业务任务；
- `judge-ds-v1` 与人类一致性未校准（缺标注样本）；
- 没有测长任务/开放创作/研究型任务——那些才可能从多候选中受益；
- 未测失败重试、预算耗尽、多 Agent 并行下的评审成本。

## 落到设计上的判断

- 候选选择保留为**能力**（复杂任务/高预算时用），不作为默认路径；
- 默认路径仍是：能确定性执行就单份，验收不过再重试/多候选；
- 要证明候选选择在业务上有用，需要“开放任务 + 校准后的 rubric + 真实数据”，这三样当前都缺。
