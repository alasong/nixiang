# 双环沉淀产物

> 这份文档回答一个问题：**跑完一轮之后，磁盘上到底留下了什么。**
> 上一版只有内存里的 list，进程一退全没了 —— 那不叫沉淀，叫临时变量。

---

## 一、七类产物

```
runs/<timestamp>/
  traces.jsonl       执行轨迹（含 facts：任务的结构化输入）
  negative.jsonl     负证据（失败路径）
  experience.jsonl   经验条目
  usage.jsonl        复用记录（哪条经验被用上、结果如何）
  retired.jsonl      淘汰墓碑（加载经验库时过滤这些 id）
  labels.jsonl       标签台账（验收结果：这条任务应判违反哪些规则）
  probes.jsonl       哨兵探针（同一任务，收敛答案 vs 探索答案）
```

样例（`runs/20261117-134751/`，跑了三条路径 90 个任务）：

| 文件 | 行数 | 大小 |
|---|---|---|
| `traces.jsonl` | 90 | 43 KB |
| `negative.jsonl` | 13 | 3.7 KB |
| `experience.jsonl` | 5 | 1.9 KB |

## 二、每条产物是什么

### 1. `traces.jsonl` —— 执行轨迹

一行一个任务，完整记录「怎么做的」。

```json
{
  "task_id": "A:EXP-003",
  "snapshot_vid": "v0",
  "verifier_vid": "vf-decisive-1",
  "outcome": "pass",
  "attempts": 1,
  "total_cost": 716,
  "steps": [{
    "node_id": "EXP-003#a1",
    "level": 0,
    "action": "extract",
    "input_hash": "49642e437e9a7998",
    "output": ["R3", "R6"],
    "judgment": "ok",
    "cost": 716,
    "latency_ms": 180,
    "nondeterministic": false
  }],
  "logged_at": "2026-11-17T05:47:51+00:00"
}
```

四个字段是它区别于「日志」的地方：

| 字段 | 作用 | 少了会怎样 |
|---|---|---|
| `verifier_vid` / `snapshot_vid` | 绑定当时用的验证器版本和规则快照 | 标准一变，历史数据无法归因，只能全部重跑 |
| `judgment` | 离散枚举（ok/retry/rule_hit/…） | 存成自然语言就无法统计、无法回放 |
| `input_hash` | 输入指纹 | 找不到「同一类任务」，也去不了重 |
| `nondeterministic` | 是否已脱离确定域 | 内环的确定性无法审计 |

### 2. `negative.jsonl` —— 负证据

只在失败时产生，**这是内环唯一的写权限**。

```json
{
  "task_id": "A:EXP-021",
  "snapshot_vid": "v0",
  "verifier_vid": "vf-decisive-1",
  "outcome": "fail",
  "reason": "attempts_exhausted",
  "node_ids": ["EXP-021#a1", "EXP-021#a2", "EXP-021#a3"],
  "input_hashes": ["e5a535d0f698981c"],
  "cost": 2148,
  "logged_at": "..."
}
```

`input_hashes` 是关键：下次遇到同样输入，先查这里，能直接判定「这条路走不通」，不用再花 2148 token 试三遍。**这是负证据唯一的价值来源。**

注意 `reason` 区分了 `attempts_exhausted`（真的走不通）和 `verifier_unknown`（验证器判不了）。这两件事混为一谈，负证据库会被污染成噪声。

### 3. `experience.jsonl` —— 经验条目

带三元组 `(trace_id, snapshot_vid, verdict)`，这是可追溯性要求。

```json
{
  "shot": {"id": "E1", "scene_tag": "tier1-high", "covers": ["R1"], "text": "金额超 5000 时…"},
  "trace_id": "manual-E1",
  "snapshot_vid": "v0",
  "verdict": {"status": "pass", "kind": "decisive", "confidence": 1.0, "detail": "manual"}
}
```

`verdict.kind` 决定它能不能进检索：`decisive` 才能，`scored` 只做审计。这条是防止评分型噪声污染 few-shot 的唯一闸门。

### 4. `labels.jsonl` —— 标签台账

验收结果的落盘：一条任务「应该被判为违反哪些规则」。写入者是**真值来源**
（验证器判定、人工复核、下游反馈），挖掘器只读——挖掘器里不存任何真值函数。

```json
{
  "task_id": "EXP-003",
  "labels": ["R3", "R6"],
  "source": "truth-engine",
  "confidence": 1.0,
  "logged_at": "..."
}
```

append-only：同一任务的新结论追加一行，读取时取最新。合成的真值引擎只是
「写入者之一」；换到真实域，换成人工复核/下游回调，`learner.learn_from_ledger`
一行不改。

### 5. `probes.jsonl` —— 哨兵探针

按比例抽任务，绕过收敛直接走探索，比对两路答案（规则集合）。一致记 `agree`，
不一致就是「收敛可能在高效地做错事」，由维护巡检报警（差异率 >5% 记 critical）。

```json
{"task_id": "EXP-003", "cached": ["R3", "R6"], "model": ["R3"],
 "agree": false, "cost": 1266, "logged_at": "..."}
```

抽样是确定性的（id + salt 的 SHA-256），同一任务集重跑抽到同一批；`rate`
是期望比例，不是严格配额。

## 三、归属：谁写、谁读

对齐契约 v2 §2 的权限矩阵：

| 产物 | 外环 Explore | 内环 Converge | 路由 Router |
|---|---|---|---|
| `traces.jsonl` | 写 | 写 | — |
| `negative.jsonl` | 写 | **写（append-only）** | — |
| `experience.jsonl` | 写 | 只读高置信层 | 读聚合统计 |
| `usage.jsonl` | 写 | **写（append-only）** | 读聚合统计 |
| `retired.jsonl` | 写 | — | 读聚合统计 |
| `labels.jsonl` | 写（验收环节） | — | 读（挖掘） |
| `probes.jsonl` | 写（监控） | — | 读（巡检） |
| 全部 | append-only，永不改写 | | |

`usage.jsonl` 是为「晋升/淘汰」补的：没有使用记录，经验条目写进去时什么样、以后还是什么样。它和负证据同类——内环记录观察到的事实，不改快照。

内环写负证据这一点，是契约 v1 修订过的 —— 原来写「内环只读」，但内环发现死路必须记下来，否则永远重复走。修订后的表述是「只读快照 + 可追加失败日志」，两者不矛盾。

## 四、能做什么（已被测试验证）

`mvp/test_integration.py`，7 个用例：

| 测试 | 验证的事 |
|---|---|
| `test_trace_is_persisted_with_both_version_ids` | 每条轨迹都带双版本号和离散判断点 |
| `test_append_only_never_rewrites_history` | 重跑不改历史行（逐字节比对） |
| `test_negative_evidence_only_on_failure` | 负证据只在失败时产生，且带输入指纹 |
| `test_experience_survives_process_restart` | 新进程能从文件完整恢复经验库并检索 |
| `test_scored_experience_is_not_retrievable` | 评分型经验进不了检索 |
| `test_trace_can_be_rejudged_after_verifier_upgrade` | **规则收紧后，旧轨迹不重跑也能按新标准重判** |
| `test_unknown_outcome_is_not_recorded_as_failure` | 三态语义：判不了 ≠ 走不通 |

第 6 条最重要。它验证的是契约 §3.2 那条硬约束：`result` 可序列化、可被任意版本验证器重判。这条不成立，「扩大可判定边界」就没有载体 —— 每次改标准都得重跑历史，成本等于重建。

测试有效性做了变异验证（改坏实现，看测试是否变红）：

| 注入的错误 | 结果 |
|---|---|
| 追加改成覆盖写 | 2 个用例失败 ✅ |
| `unknown` 记成 `fail` | 1 个失败 ✅ |
| 不落盘 | 2 个失败 ✅ |
| 不区分置信层 | 1 个失败 ✅ |

全绿不等于有效。这四个变异证明测试确实在测东西。

## 五、没实现的部分（必须说清）

沉淀物有了，消费方也接上了一部分（挖掘读「轨迹 + 台账」，晋升/淘汰/快照在
维护回路里跑）。真正没接的是**真实域**：

| 缺什么 | 后果 |
|---|---|
| **真实域的标签来源** | 台账写满了，但合成域里写它的是真值引擎；真实业务要接人工复核/下游回调 |
| **覆盖率阈值标定** | 台账覆盖 < 50% 不学（硬门已接），但 50% 是拍的，真实域要按标注成本标定 |
| **监控探针（哨兵/无偏采样/对抗样本）** | 收敛做错事时没有在线发现机制（§8 监控只落了验证器回归） |
| **目标形式化** | 任务直接以文本进来，没有「转成可判定命题」这一环 |

所以准确说法是：

> **管道通了、消费方接上了；沉淀的内容仍然只有合成域这一份。**

跑出来的轨迹与台账都来自仿真模型和合成真值。它们的价值是证明「格式对、
链路通、能恢复、能重判、能回流成规则」，不是证明「这些数据在业务上有用」。

**要让它有用，只有一个前提：接上真实模型和真实任务，跑够量，并由真实验收写台账。** 这又回到 REAL_DATA_REPORT 第六节那个结论 —— 你现在缺的是数据，不是管道。

## 六、复现

```bash
python3 -m mvp                                  # 跑主流程，产物落在 runs/<时间戳>/
python3 -m mvp.loop.learner --demo              # 轨迹 + 标签台账 → 挖掘 7/7
python3 -m unittest mvp.tests.test_integration -v  # 7 个集成测试
python3 -m unittest mvp.tests.test_mvp -v          # 15 个单元测试
```

读回产物：

```python
from mvp.core.persistence import RunStore, replay_verdict
s = RunStore("runs/20261117-134751")
traces = s.load_traces()          # 90 条
neg = s.load_negative()           # 13 条
exp = s.load_experience()         # 可直接 retrieve
```
