# 融合双环架构 设计文档

**版本** v1.0 ｜ **状态** 待评审 ｜ **日期** 2026-11-17
**取代** v0.1（`双引擎逆向推理设计文档.md`）的定位，v0.1 保留作为演进记录

---

## 0. 定位修正（相对 v0.1）

v0.1 的定位是"把可复用判断固化成规则，压低成本"，本质是**成本优化工程**。v1.0 改为**双环系统**：一个快环负责在已知空间内低成本做对，一个慢环负责持续扩大已知空间。

同时修正三处表述：

| v0.1 说法 | 问题 | v1.0 修正 |
|---|---|---|
| 追求"任务最优" | 不可判定 | 改为"预算约束下的近似最优"，度量口径明确为成本/质量双指标 |
| "闭环系统" | 易被误读为自足 | 改为**逻辑封闭 + 系统开放**，明确是开放系统 |
| 规则库是核心资产 | 规则是破坏性压缩 | 规则降为配件，**验证器与经验库**是主干资产 |

## 1. 三个前提假设

整套设计的有效性依赖三条假设。**任何一条不成立，方案终止。** 这三条必须在 MVP 阶段被验证，不能默认成立。

| 编号 | 假设 | 若不成立的后果 | 验证方式 |
|---|---|---|---|
| H1 | 存在任务分布：同类任务反复出现，簇内样本 ≥5 | 经验库无法检索，收敛路径永远无路可走，系统退化为"高预算跑模型" | 对 50 个真实任务做聚类，看是否形成 5-8 个明显簇 |
| H2 | 存在判定型验证器，且覆盖率足够 | 只能用评分型，信号带噪，学到的是"讨好评分器" | 统计可改造为客观判定的任务比例 |
| H3 | 复用能降本且不掉质量 | 收益不成立，整个方案没有存在理由 | MVP 对照实验，见 §6 |

**H1 优先级最高**，它决定"该不该做"，其他两条决定"怎么做"。

## 2. 总体架构：双环嵌套

```
┌──────────────────────── 外环：进化（周级，随机） ────────────────────────┐
│                                                                          │
│   探索模式 Explore                                                       │
│     检索经验 · 放开采样 · 高预算 · 全量记录                                │
│     产出：成功轨迹 / 失败归因 / 新的可判定条件                             │
│                          │                                               │
│                          ▼                                               │
│              ┌───────────────────────┐                                   │
│              │  验证器（共享，版本化）│                                   │
│              └───────────────────────┘                                   │
│                          │                                               │
│              ┌───────────────────────┐                                   │
│              │  经验库（分层置信）    │──提交新事实/规则──┐                │
│              └───────────────────────┘                   │                │
└──────────────────────────────────────────────────────────┼───────────────┘
                                                           ▼
                                             ┌──────────────────────┐
                                             │  封闭世界快照 v_n     │
                                             │ （不可变，只读）      │
                                             └──────────────────────┘
                                                           │
┌──────────────────────── 内环：执行（秒级，确定） ─────────┼───────────────┐
│                                                          ▼               │
│   收敛模式 Converge                                                      │
│     目标形式化 → 正向短路 → 逆向展开 → 规则命中 → 低预算                  │
│     特性：同输入必同输出，可完整重放                                      │
│                                                                          │
└──────────────────────────────────────────────────────────────────────────┘
```

### 2.1 双环的分工与隔离

| | 内环 Converge | 外环 Explore |
|---|---|---|
| 目标 | 同输入同输出，成本最低 | 分布变化时行为跟着变 |
| 依赖 | 快照 + 规则 + 逆向链 | 检索 + 采样 + 验证器 |
| 确定性 | **必须确定** | **必须有随机性** |
| 预算 | 主池（85-95%） | 探索池（5-15%，按域动态） |
| 周期 | 秒级 | 周级 |
| 失败含义 | 该路径不可用，记负证据 | 正常，是信息 |

**两条硬约束：**

1. **探索逻辑不得进入内环**。内环里出现任何随机性，可复现性即失效，负证据也不可信。
2. **内环只读快照**。推理过程中快照不可变，否则回溯时状态错乱。

### 2.2 封闭世界快照

推理必须在一个**一致的封闭世界**上进行，这是逆向链能给出确定否定结论的前提（开放世界下只能说"推不出"，业务上不可用）。

实现：快照是事实库 + 规则库 + 验证器版本的不可变组合。探索产出新事实/规则后，提交生成新快照，内环仍读旧快照直至下一次刷新。

```
探索 ──提交──▶ snapshot v_n+1
                    │
内环 ◀──只读 v_n ────┘
```

快照必须带 `vid`，所有轨迹记录"当时由哪个 vid 判定"。验证器或规则变更后，历史轨迹的标注视为过期，需重算或标记。

## 3. 关键流程

### 3.1 一次任务的完整生命周期

```python
def handle(task):
    snap = snapshot.current()                    # 1. 取一致快照
    route = router.decide(task, snap)            # 2. 路由

    if route == CONVERGE:
        try:
            r = converge(task, snap)
            if verifier.check(r, snap.vid):      # 3. 验收（外置）
                recorder.record(task, r, "converge")
                return r
        except ReuseFailure as e:
            recorder.mark_negative(e, snap.vid)  # 4. 负证据
        route = EXPLORE                          # 5. 降级

    r = explore(task, snap)                      # 6. 探索
    ok = verifier.check(r, snap.vid)
    recorder.record(task, r, "explore", ok)

    if ok:
        miner.offer(task, r, snap.vid)           # 7. 产出候选
    return r
```

三个关键点：**验收在两条路径上完全共用**（同一个 `verifier`、同一个 `vid`）；**失败只降级不重来**（不整体重规划）；**探索产物必回流**（`miner.offer`，不回流等于白花钱）。

### 3.2 内环：收敛

```python
def converge(task, snap):
    goal = formalize(task)                       # 目标形式化
    if snap.closure_has(goal):                   # 正向短路
        return ok(proof=[])

    for b in engine.expand(goal, snap, W, D):    # 逆向展开，限宽限深
        sub = allocator.split(b, remaining)
        if all(converge(s, snap).ok for s in b.subgoals):
            return ok(proof=b)
    raise ReuseFailure(evidence=...)
```

**目标形式化是外环职责**：`formalize` 的结果应缓存进经验库，同一类任务第二次走 converge 时直接复用，不再调用模型。这一步是 H2 之外最容易卡死的地方——形式化失败的任务直接进探索，不要硬凑。

### 3.3 外环：探索

```python
def explore(task, snap):
    shots = experience.retrieve(task, k=3, min_conf=HIGH)   # 只用高置信层
    cands = llm.sample(task, shots, n=N, temp=HIGH)
    return best_of(cands, verifier, snap.vid)               # 用验证器挑
```

**检索必须限置信层**。低置信层的轨迹（仅评分型通过）会污染 few-shot，即使它们看起来相似。

### 3.4 路由判据

| 条件 | 路由 |
|---|---|
| 该任务族 ≥N 条成功轨迹，且验证器为判定型 | CONVERGE |
| 经验库空 / 验证器仅评分型 / 目标形式化失败 | EXPLORE |
| CONVERGE 连续失败 ≥2 次 | 降级 EXPLORE |
| EXPLORE 同族连续成功 ≥3 次 | 晋升候选（需人工确认后生效） |

晋升必须留人工确认。自动晋升会让一条偶然成功的路径变成默认路径，而它可能只是运气。

## 4. 组件清单与优先级

| 组件 | 职责 | MVP | 优先级 |
|---|---|---|---|
| Recorder | 结构化轨迹，含 vid、judgment、失败归因 | ✔ | P0 |
| Verifier | 验收判定，分判定型/评分型，版本化 | ✔ | P0 |
| ExperienceStore | 经验检索，按置信度分层 | ✔ | P0 |
| Router | 收敛/探索路由 | ✘ | P2 |
| BackwardEngine | AND-OR 展开、回溯、剪枝 | ✘ | P3 |
| RuleStore | 规则生命周期、冲突仲裁 | ✘ | P3 |
| BudgetAllocator | 预算池切分与节点分配 | ✘ | P4 |
| Miner | 从轨迹挖候选规则 | ✘ | P4 |
| Sentry | 哨兵任务，校验快照有效性 | ✘ | P2 |
| Evaluator | held-out 评测环 | ✘ | P1 |

**MVP 只要三个组件**：Recorder、Verifier、ExperienceStore。其余全部推后。

---

## 5. 复杂度纪律

这套设计天然倾向膨胀——每加一条对策（哨兵、版本化、无偏采样、双池），复杂度 +1，边际收益递减。

**约束：同时存在的可动部件不超过 7 个。** 超过则必须先合并或下线一个。

理由很实际：系统的存活前提是维护者能在脑子里装下全部部件。装不下就会出现"没人敢改"，然后冻结在一个能跑但不优化的状态，比不做还糟。

## 6. MVP 定义

### 6.1 目标

只验证 H3（复用能否降本且不掉质量），顺带为 H1/H2 收集证据。**不验证"系统能跑通"**——那是必然的，没有信息量。

### 6.2 范围

| 项 | 内容 |
|---|---|
| 任务域 | 1 个任务族，20-30 个真实样本 |
| 经验 | **手工建 5-10 条**，不自动挖掘 |
| 验证器 | 只做判定型，评分型一律不碰 |
| 路径 | 基线（纯 LLM，无经验）vs 增强（LLM + 检索经验） |
| 路由 | **手动切换**，不做自动路由 |
| 记录 | 全量 Recorder |

### 6.3 明确不做

逆向链 · 规则库 · 自动调度 · 探索预算 · 微调 · 升降级 · 哨兵 · 无偏采样

### 6.4 验收指标

| 指标 | 阈值 | 度量 |
|---|---|---|
| 成本降幅 | ≥ 40%（token 计） | 同批样本，两路径对比 |
| 成功率 | 下降 ≤ 5% | 验证器判定 + 人工复核 20% 样本 |
| 复用误伤 | 无系统性错误 | 人工逐条确认增强路径的失败样本 |

### 6.5 Kill Criteria

| 触发 | 结论 |
|---|---|
| 成本降幅 < 20% | 收益不成立，停 |
| 成功率下降 > 10% | 质量不可接受，停 |
| 聚类检验显示无分布 | 前提不成立，整个方案换向 |
| 判定型验证器覆盖 < 40% | 信号不足，先解决验证器再做系统 |

**必须在开工前写死这四条。** 没有 kill criteria 的不是 MVP，是缩小版产品。

### 6.6 工期

5-8 人日。超过 10 人日说明范围没砍够。

## 7. 演进路径

```
MVP（三组件）
  │  H3 成立
  ▼
+ Evaluator（held-out 环）        ← 先建度量，再谈优化
  │
  ▼
+ Router + Sentry                  ← 自动路由，同时上保险
  │
  ▼
+ BackwardEngine + RuleStore       ← 逆向链与规则
  │
  ▼
+ BudgetAllocator + Miner          ← 预算分配与自动挖掘
  │
  ▼
+ 微调（最后）
```

每一步都要求前一步的指标稳定，不允许并行推进。**微调排最后**，因为在验证器不稳、数据量不足时微调，得到的是一个很快过期的权重，而真正该积累的资产（数据 + 验证器）还没建起来。

## 8. 运行时监控

融合系统的失效是渐进的，不会报错。必须有主动探针。

| 监控项 | 手段 | 触发动作 |
|---|---|---|
| 快照过期 | 哨兵任务：固定 1% 真实任务绕过收敛，强制走探索，比对两条路径结果 | 差异率超阈值 → 全量重校 |
| 探索样本偏倚 | 保留一部分任务不经路由筛选，纯随机抽样进探索 | 分布偏移超阈值 → 调整路由 |
| 验证器漂移 | 已知答案样本集定期回归 | 回归失败 → 冻结该版验证器 |
| 评分器被利用 | 定期喂"看起来对但实际错"的对抗样本 | 识别率下降 → 换评分器或降级为辅助 |

**哨兵任务是最便宜的保险**，不到 1% 预算，但能挡住"收敛高效地做大范围错事"这个最致命的问题。只做一件事的话，做这个。

## 9. 风险登记

| 编号 | 风险 | 等级 | 缓解 |
|---|---|---|---|
| R1 | H1 不成立（无任务分布） | 高 | MVP 前做聚类检验，一天出结果 |
| R2 | 验证器本身错误且不可见 | 高 | 验证器回归 + 对抗测试；判定型优先进高置信层 |
| R3 | 收敛放大错误（效率越高错得越整齐） | 高 | 哨兵任务 |
| R4 | 成功锁死：越成功探索样本越偏 | 高 | 无偏随机采样 |
| R5 | 元层级参数无信号（阈值、比例靠拍） | 中 | 全部进 A/B 框架，禁凭直觉改 |
| R6 | 复杂度膨胀超出维护能力 | 中 | 部件数上限 7 |
| R7 | 业务规则在本域天然有争议，判定型难做 | 中 | 承认定位为"辅助"，不承诺全自动闭环 |
| R8 | 归因被稀释（五处可能出错，外部表现一致） | 中 | 每个决策点记 decision_id + 上游依赖 |

## 10. 开放问题

1. **目标形式化的自动方法**：把模糊诉求转成可判定命题，目前只能靠模板 + 人工，无通用方案。这是框架外的一环但决定上限。
2. **真值来源**：除人工复核外，是否存在低成本外部真值（下游系统反馈、日志比对）？决定 R2 能否真正缓解。
3. **跨域规则迁移**：A 域经验能否复用到 B 域？能则边际成本大降，不能则每域重建。
4. **模型升级时的经验迁移**：底层模型换代后，旧经验可能整体失准。经验和验证器可迁移，权重不可。

---

## 11. 一句话总结

> 这是一个**在可版本化封闭世界上工作的开放系统**。封闭是每次推理的局部姿态，开放是系统长期的生存方式。内环保证"这次做得对"，外环保证"以后还对"。
